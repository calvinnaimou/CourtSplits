# courtSplitz

NBA statistical trend-analysis web app. Users search by player or team, set filters and stat thresholds, and get historical occurrence-rate/box-score data. Framed explicitly as **analytics, not a sportsbook/bet tracker** — but the underlying data does include real historical betting lines (spread/total/moneyline) and the app surfaces them (see "Odds Data" below).

Formerly named `fpfl`; directory renamed to `courtSplitz` on 2026-08-10. If anything under `.venv/bin/` fails with "No such file or directory" even though `.venv/bin/python3` works, it's a stale shebang from before the rename — grep `.venv/bin/` for `/Users/calvinnaimou/fpfl` and sed-replace, don't reinstall the venv.

## Stack & how to run

- **Backend**: Python 3.13 + pandas + FastAPI. Historical seasons (2025-26, finished) live in committed Parquet files, loaded once via `lru_cache` in `engine/data.py` — no ORM. The live/current season (2026-27+) is a hybrid: those same functions also merge in rows from Postgres when `DATABASE_URL` is set, refreshed on a short TTL cache instead of `lru_cache` since that data actually changes. See "Live season data" below — without `DATABASE_URL` set, behavior is identical to the old parquet-only setup.
- **Frontend**: TypeScript + React (Vite), no router library — view switching is local `useState` in `App.tsx`.
- Backend: `.venv/bin/uvicorn api.main:app --app-dir /Users/calvinnaimou/courtSplitz --port 8000 --reload` (serves `http://127.0.0.1:8000`, Swagger at `/docs`).
- Frontend: `cd frontend && npm run dev` (serves `http://localhost:5173`, reads `VITE_API_BASE_URL` from `frontend/.env`).
- Tests: `.venv/bin/python3 -m pytest tests/ -q` — 127 passing as of 2026-08-14 (plus 6 more in `tests/test_live_db.py`, gated behind `TEST_DATABASE_URL` — see "Live season data").
- Frontend typecheck: `cd frontend && npx tsc -b --noEmit`.
- **Important**: `engine/data.py` caches parquet DataFrames in memory via `@lru_cache`. If you regenerate the parquet files (re-run `scripts/preprocess.py`), the running uvicorn process will keep serving stale data until restarted — `--reload` only watches `.py` source files, not the data files.
- **Verifying frontend changes**: use Playwright via a throwaway `.mjs` script in `frontend/` (launch, interact, assert, delete the script after) — this has been the reliable pattern all session for confirming a fix actually works in a browser, not just that it compiles.

## Data pipeline

- Raw source: two Excel workbooks in `data/raw/` from **BigDataBall** (paid provider, not a live API — static `.xlsx` files, no API keys). `2025-2026-NBA_Player_BoxScore-Dataset.xlsx` (28,716 rows, includes a `DNP-DND-NWT` sheet and a `TEAMS` sheet) and `2025-2026_NBA_Team_BoxScore-Stats.xlsx` (2,644 rows, one row per team per game — includes real historical betting lines).
- `scripts/preprocess.py` reads the raw Excel and writes `data/processed/*.parquet` (`player_boxscore`, `player_dnp`, `team_boxscore`, `teams`). Re-run it whenever raw data or the position-override logic changes, then **restart uvicorn**.
- Every column in the raw sheets is a straight rename (see the dict at the top of each `preprocess_*` function in `preprocess.py`) plus a handful of derived columns (win, margin, combined_total, covered_spread_*, pra/pts_reb/reb_ast, is_back_to_back, days_rest_bucket, season_type from the game_id prefix).

## Live season data (2026-27+)

The 2025-26 season is finished and frozen — its parquet files are committed to git and never change. The 2026-27 season (and presumably each one after) works differently, since BigDataBall will sync a daily-updated workbook (~5am ET) into a Google Drive folder once that season starts, and the app needs to reflect new games without a code deploy each day. Added 2026-08-14, before the 2026-27 season existed — the Drive-specific half of this is unverified against a real folder (see below).

- **`engine/live_db.py`**: `fetch_live_rows(table, database_url)` reads one of the 3 live tables from Postgres into a DataFrame (dtypes cast to match the parquet ones exactly, so concatenating the two doesn't silently upcast a column), returning `None` on any failure — a DB hiccup falls back to historical-only, never a 500. `TTLCache` re-fetches at most once per `LIVE_DATA_TTL_SECONDS` (default 3600) instead of caching forever like `lru_cache` would.
- **`engine/data.py`**: `player_boxscore()`/`player_dnp()`/`team_boxscore()` merge historical parquet + live Postgres rows (deduped on game_id, live wins on conflict) only when `DATABASE_URL` is set in the environment — unset, they're byte-identical to the old parquet-only functions. `teams()` has no live counterpart (30 static rows, doesn't change mid-season).
- **`db/schema.sql`**: hand-written DDL for the 3 live tables (`player_boxscore`, `player_dnp`, `team_boxscore`), no migration framework. Run once by hand against a fresh Postgres: `psql "$DATABASE_URL" -f db/schema.sql`.
- **`scripts/ingest_live_data.py`**: loads a BigDataBall workbook into Postgres. Re-runs the full `preprocess_*()` pipeline over the *whole* file every time and does `TRUNCATE` + reload per table in one transaction — not an incremental upsert, since `team_rest_gaps()` needs full-season context and the team rows are derived by self-merging each game's two teams together, so partial data would compute wrong. Assumes the daily file is cumulative (whole season to date), not a delta — inferred from how the existing full-season files are shaped, not yet confirmed for the live file. Independently useful today: run it by hand against any BigDataBall workbook, no Drive integration required. Tested end-to-end against a real local Postgres (Homebrew `postgresql@16`) using the actual 2025-26 raw files as a dry run — round-tripped cleanly, no type-adaptation issues.
- **`scripts/preprocess.py`**: the three `preprocess_*` functions now take a file path + sheet name (defaulting to today's hardcoded 2025-26 values), so `ingest_live_data.py` can reuse them against any workbook. Refactor verified byte-identical output via diffing before/after.
- **Unverified until the season actually starts** (`scripts/fetch_from_drive.py`, `.github/workflows/daily-refresh.yml`): downloading from Drive itself. Kept deliberately small and isolated (Google API libraries imported only inside that one file, not in `requirements.txt`) so an unfinished/broken Drive integration can't affect the running app or test suite. Needs, once the Drive folder exists: a Google Cloud service account (JSON key) shared on that folder, its ID, and confirmation the daily file really is cumulative and that next season's sheet names match the guessed `NBA-2026-27-PLAYER`/`NBA-2026-27-TEAM` pattern.
- Local dev/testing needs a real Postgres — `tests/test_live_db.py` is skipped unless `TEST_DATABASE_URL` is set (see that file's docstring for the one-time `createdb`/`psql -f db/schema.sql` setup).

### Data quirks worth knowing before "fixing" something that looks wrong

- **`is_back_to_back`** and **`team_rest_days_raw`**: neither is BigDataBall's literal value anymore (the `_raw` suffix on the latter is a holdover name, not a promise of rawness). Both are computed by `team_rest_gap()`/`team_rest_days_bucket()` in `preprocess.py` directly from the calendar gap between a team's consecutive games in the dataset — deliberately *not* by pattern-matching BigDataBall's raw `TEAM REST DAYS` text tag (`1`, `2`, `3+`, `3IN4`, `3IN4-B2B`, `4IN5-B2B`, `B2B`), because that tag encodes schedule *context* ("3rd game in a 4-day stretch") rather than the rest count itself, and pattern-matching it turned out to be unreliable: a `3IN4`-tagged game can be either the stretch's last leg (coming off a back-to-back, 1 day rest — the common case, ~99.7% of `3IN4` rows) or its first leg (2+ days rest before it). Caught 2026-08-13 by spot-checking against the real schedule on basketball-reference.com: a `3IN4`-tagged Chicago game on 2026-01-10 actually had 2 days of rest (not 1), and a `1`-tagged Miami game the same day actually had 3 (BigDataBall's own tag was simply wrong there — confirmed by the real schedule showing no game in between). Full-dataset comparison against the old tag-based values: `is_back_to_back` was already 100% correct (2644/2644 — "B2B" unambiguously means 0 rest by definition, so this needed no fix), and the rest-day bucket changed for exactly the 2 rows above (2642/2644 unchanged). Bucket values are `1`/`2`/`3+`/`B2B`; `B2B` stands in for 0 days since that's the term used throughout the team screens, and a team's first tracked game (no prior game to diff against) buckets to `3+`.
- **`halftime`, `opening_odds`, `closing_odds`, `line_movement_1/2/3`**: raw mixed-format strings like `"114.5u 15"` (total, over, +115 price) or `"-4 -05"` (spread -4, -105 price). Which row (home/away) gets the spread vs. the total is **not reliable by home/away** — it varies per game. The only robust signal found: magnitude — spreads are essentially always ≤20, half-totals are essentially always ≥80 (see `parseLeadingNumber`/`halfTotalEntry`/`halfSpreadEntry` in `GameDetailModal.tsx`). Full-game `opening_spread`/`closing_spread`/`opening_total`/`closing_total`/`moneyline` are separate, already-clean numeric/string columns — prefer those over parsing the mixed strings when possible.
- **Team perspective duplication**: `team_boxscore` has **two rows per game** (one per team). When a team query isn't pinned to a specific `team_name`, the pool can double-count a game if a shared stat (e.g. `closing_total`) hits on both rows. This is why the UI shows `"X occurrences matched"` (no fraction) when no team/player is pinned, vs. `"X of Y (Z%)"` when one is — see "Result-count display rule" below.
- **`position` column**: see the dedicated section below — it's now a layered override, not the raw BigDataBall value in most cases.

## Architecture

- `engine/query.py` — the core stats engine. `query_player()`, `query_team()`, `player_season()`. Pure functions: DataFrame + filter params in, plain dict out, no web concerns. Conditions are `{metric or periods, threshold, direction: over|under|equals, inclusive: bool}` — `over`/`under` default **inclusive** (`>=`/`<=`); `inclusive: false` makes them strict. `query_player` always requires ≥1 numeric condition; `query_team` doesn't (a purely categorical search like "all games vs the Grizzlies" is valid) but requires **team_name OR at least one other filter** — not "team required." Both support pagination (`page`/`page_size`, default 50/max 500) — `sample_size`/`hits`/`conditions` always describe the *full* matching pool; only the `games` list is sliced, since that's the expensive part (building the full per-row stat line for every hit). A prior version eagerly embedded a full nested `game_detail()` box score in every hit row (`full_game_stats`) — this was dead weight nobody read (the modal fetches lazily on click) and crashed on loose filters like "PTS over 5, no player" (20k+ rows); it was removed entirely, not just paginated.
- `engine/game_detail.py` — `game_detail(game_id)`: full box score for one game (both teams' stats, every player, DNPs with reason). Powers `GET /games/{id}`, called lazily when the frontend's "Game" button is clicked — never eagerly.
- `api/main.py` / `api/schemas.py` — FastAPI layer. Pydantic validates `page`/`page_size` bounds (422 on violation, before the engine's own `ValueError` 400s ever run). `round_to_half()` in `schemas.py` snaps free-typed numeric thresholds to the nearest 0.5.
- `frontend/src/App.tsx` — root: logo image, Player/Team tab switcher, view state (`playerSearch | teamSearch | playerSeason`), shared `GameDetailModal`.
- `frontend/src/statFilters.ts` / `teamStatFilters.ts` — **single source of truth** for stat filter labels/order/metric-name mapping, consumed by the search filter grids, results tables, season averages, and the game modal's per-player/per-team tables alike. Player order: PTS, ORBS, DRBS, TRBS, AST, PRA, PR, AR, FGM, FGA, 3PM, 3PA, FTM, FTA, STL, BLK, TO, PERFOUL, MIN, then USAGE RATE (%)/REST DAYS. Team order: TOT PTS, 1Q–OT2 PTS (OT3-5 intentionally excluded, never occurred this season), OPP PTS, MARGIN, TOTAL, MIN, shooting splits, rebounds, AST, PERFOUL, STL, TO, TO TOTAL, BLK, POSS, PACE, OEFF, DEFF.
- `frontend/src/components/PlayerSearchPage.tsx` / `TeamSearchPage.tsx` — the two search screens. Team screen dynamically disables (greys to "N/A") any stat-filter cell whose metric isn't in `/teams/metrics` (e.g. OT columns that never occurred), so the UI can't submit a request the backend would 400 on.
- `ResultsTable.tsx` / `TeamResultsTable.tsx` — results tables. **Row keys must be `game_id + identity` (e.g. `${game_id}-${team}` or `${game_id}-${player_name}`), never `game_id` alone** — a real bug shipped from using bare `game_id` as the React key in `TeamResultsTable`, since an unpinned team query returns two rows (one per team) sharing a `game_id`; duplicate keys broke React's list reconciliation and left stale rows on screen after a new search. Fixed 2026-08-13.
- `PlayerSeasonPage.tsx` — one player's full game log for a season scope (regular/playoffs/both, defaults regular), reached by clicking a player's name in results. Player name isn't repeated per-row there since it's already the page title.
- `GameDetailModal.tsx` — lazy-fetches `GET /games/{id}` on open. Sections, top to bottom: date + season label → **Odds Data** → **Team Stats** → per-team player box scores + DNP list (with real reason, e.g. "COACH'S DECISION", not just status).
  - **Odds Data**: only spread, total, moneyline, halftime shown (opening/closing *odds* and line-movement columns removed — the embedded price, e.g. `-07`, is meaningless without knowing the other side's price, so it's stripped). Total shown **once** per game (not duplicated per team row, since it's a shared stat) as `"213.5 (Over)"`, opening only (closing dropped per user request). Spreads show an explicit `+` for the underdog (`+1.5` not `1.5`) so it doesn't read ambiguously next to the favorite's `-1.5`. Winning side highlighted green using the backend's precomputed `win`/`covered_spread_opening` fields — never guessed client-side. **Half bets are computed, not parsed from the raw `halftime` string**: real half score = `q1 + q2` per team, compared against the half line extracted via the magnitude heuristic above; shown as a "Half Total" line and a "Half Spread" column (derived signed spread, not the raw score) with the covering side highlighted green.
  - **Team Stats**: one row per team, same columns as a Team-search result row (reuses `TEAM_STAT_FILTERS`) — added so a player-search user sees the same team-level row a team-search user would have seen for that game.
- `Pagination.tsx` — shared Previous/Next component used by both search pages.

## Position data (layered override system)

BigDataBall's raw `POSITION` column tags positional *versatility*, not roster position — e.g. Jokić gets clean `C`, but Embiid/Wembanyama/Holmgren/Davis get combo tags like `C-F` despite being widely known as single-position players (confirmed deliberate, not noisy, by checking several players). The user wanted more accurate/granular positions. Basketball-Reference (which has the full PG/SG/SF/PF/C scheme) **blocks all automated fetching** (confirmed 403 on player pages, team roster pages, and even the bulk league-wide stats page) — not fixable by retrying. NBA.com timed out (JS-heavy). Wikipedia works but only has the simpler G/F/C scheme.

Resolution: `data/processed/NBA_Player_Positions.xlsx` is a **manually-provided sheet** (435 players, columns `Player`/`Position`, values `PG`/`SG`/`SF`/`PF`/`C`) the user exported from Basketball-Reference themselves. `scripts/preprocess.py` applies a **layered override** (`apply_position_overrides()`), most-trusted first:

1. This Basketball-Reference sheet (detailed PG/SG/SF/PF/C) — 424/582 players matched, after normalizing name suffixes (Jr./Sr./II-V), punctuation, and **diacritics** (Jokić→jokic, Dončić→doncic — 18 players needed this).
2. `data/processed/missing_players_positions_filled.xlsx` — a second manually-provided sheet (columns `Name`/`Position`, same detailed PG/SG/SF/PF/C scheme), covering specifically the players the BRef sheet doesn't. Added 2026-08-13; between the two sheets, coverage is 424 + 158 = 582 players — exactly the full unique-player count in the box score data, zero overlap, zero gaps (verified by hand and pinned down in `tests/test_data_integrity.py`).
3. `scripts/espn_positions.py` — a static snapshot (fetched 2026-08-12 from all 30 teams' ESPN roster pages, simpler G/F/C scheme). Shouldn't actually get used anymore now that #1+#2 cover everyone, but stays as a fallback.
4. BigDataBall's original raw value, last resort if a future player shows up in none of the above (e.g. a new call-up not yet added to either manual sheet).

All override sources are **static snapshots baked in at preprocessing time, not live-fetched at runtime** (explicit user instruction — don't re-fetch on every app run). If rosters change significantly, re-fetch ESPN and/or ask the user for a fresh Basketball-Reference export (or an update to the missing-players sheet) for any new players, then re-run `preprocess.py` and restart uvicorn. Two players (LeBron James, Anthony Davis) show a different *team* on ESPN's live roster than our season-long dataset reflects — a real trade after this assistant's knowledge cutoff, not a scraping error; irrelevant here since only their *position* value is used, which is stable.

## Product/UX rules locked in (don't re-litigate without reason)

- Never show a percentage without its sample size.
- **Result-count display rule**: entity pinned (team_name/player_name given) → `"X of Y games matched (Z%)"`. No entity pinned (browsing) → `"X occurrences matched"`, no fraction — see the team-row-duplication quirk above for why a percentage would be misleading there.
- Season-type toggle: regular/playoffs/both, default both (player season page defaults to regular only).
- "Over X" means `>= X` by default; a global "Inclusive thresholds" checkbox (not per-filter) toggles strict `>`/`<`.
- Numeric decimals snap to nearest 0.5 server-side (`round_to_half` in `api/schemas.py`).
- Any UI input for a metric the backend would reject (e.g. a stat that never occurred this season) should be disabled/greyed with an explanation, never allowed to submit and 400.
- Deferred, not fixed: on the Team screen, the top "TOT PTS" field (full-game final score) is a separate mechanism from the Q1–OT2 period checkboxes below it — checking a period box does nothing until "COMBINED PERIODS TOTAL" also has a number typed in. User chose to leave this for a planned in-app help page rather than change the UI.
- No logos/favicons except ones the user made — the default Vite favicon and an unused scaffold `icons.svg` were removed; `frontend/public/CourtSplitzLogo.png` (user-provided) renders at the top of both search screens via `App.tsx`.
